# Домашнее задание: Компоненты Kubernetes — расчёт требований к кластеру

## Постановка задачи

Приложение состоит из четырёх компонентов:
- **База данных** — отказоустойчивая, 3 реплики, по 4 ГБ ОЗУ и 1 ядру на реплику.
- **Кеш** — отказоустойчивый, 3 реплики, по 4 ГБ ОЗУ и 1 ядру на реплику.
- **Frontend** — 5 реплик, по 50 МБ ОЗУ и 0.2 ядра на реплику.
- **Backend** — 10 реплик, по 600 МБ ОЗУ и 1 ядру на реплику.

Нужно определить, сколько worker-нод (и какого размера) потребуется кластеру, чтобы выдержать эту нагрузку с запасом на отказ одной ноды, плюс учесть служебные ресурсы control-plane.

---

## Шаг 1. Расчёт сырых требований по компонентам

| Компонент | RAM / экземпляр | CPU / экземпляр | Реплик | RAM итого | CPU итого |
|---|---|---|---|---|---|
| База данных | 4 ГБ | 1 | 3 | 12 ГБ | 3 |
| Кеш | 4 ГБ | 1 | 3 | 12 ГБ | 3 |
| Frontend | 0.05 ГБ (50 МБ) | 0.2 | 5 | 0.25 ГБ | 1.0 |
| Backend | 0.6 ГБ (600 МБ) | 1 | 10 | 6 ГБ | 10 |
| **Итого** | | | | **30.25 ГБ** | **17 ядер** |

Это «сырая» суммарная потребность — сколько ресурсов должно быть доступно для планирования подов (`requests`) без учёта отказов и служебных нужд самого кластера.

---

## Шаг 2. Выбор размера worker-ноды


- **Слишком крупные ноды** — при выходе из строя одной ноды теряется сразу большая доля кластера («blast radius»), и планировщику сложнее эффективно упаковать поды без «застрявших» неиспользуемых остатков ресурсов.
- **Слишком мелкие ноды** — непропорционально много ресурсов уходит на служебные нужды каждой ноды (kubelet, container runtime, ОС, агенты мониторинга/логирования), а также растёт количество нод, которые нужно администрировать.

Самый крупный отдельный под в системе — это реплика БД/кеша (4 ГБ / 1 ядро). Нода должна быть в несколько раз больше самого крупного пода, чтобы на неё помещалось несколько разных подов одновременно, но не быть чрезмерно огромной. Выбираем практичный средний размер:

**Worker-нода: 8 vCPU / 32 ГБ ОЗУ**

### Служебные ресурсы (system-reserved / kube-reserved)

На каждой worker-ноде часть ресурсов должна быть зарезервирована под:
- `kubelet` и container runtime (containerd/CRI-O),
- операционную систему,
- служебные агенты (мониторинг вроде node-exporter, сбор логов вроде fluentbit/promtail, CNI-плагин и т.п.).

Для ноды 8 vCPU / 32 ГБ закладываем резерв **1 vCPU и 2 ГБ ОЗУ** (примерно 12% CPU и 6% RAM).

**Относительные значения ресурсов на worker-ноду: 7 vCPU / 30 ГБ ОЗУ.**

---

## Шаг 3. Минимальное количество worker-нод (без учёта отказа)

```
По CPU: 17 ядер / 7 vCPU на ноду  = 2.43 → округляем вверх → 3 ноды
По RAM: 30.25 ГБ / 30 ГБ на ноду  = 1.01 → округляем вверх → 2 ноды
```

Берём максимум из двух оценок (узкое место — CPU): **минимум 3 worker-ноды**, чтобы вообще разместить всю нагрузку.

*(Важно: 3 ноды нужны в любом случае ещё и по другой причине — отказоустойчивые компоненты, БД и кеш, должны располагаться на РАЗНЫХ нодах через anti-affinity/`topologySpreadConstraints`. Если все 3 реплики БД окажутся на одной ноде, отказ этой ноды убьёт весь компонент целиком, несмотря на «3 реплики» в конфигурации. Поэтому даже без учёта общей загрузки по ресурсам нужно минимум 3 ноды под сами реплики.)*

---

## Шаг 4. Запас на отказ одной ноды

Отказоустойчивость кластера означает: если ЛЮБАЯ одна нода выйдет из строя, оставшиеся ноды должны быть способны вместить всю нагрузку (планировщик Kubernetes перепланирует поды с упавшей ноды на живые). Формально: при `N` worker-нодах должно выполняться условие

```
(N - 1) × allocable_на_ноду  ≥  суммарная_потребность
```

Проверяем для `N = 3` (минимум из Шага 3):
```
(3 - 1) × 7 vCPU = 14 vCPU  <  17 vCPU нужно  →  НЕДОСТАТОЧНО
```
3 ноды не проходят проверку на отказоустойчивость — при потере одной ноды из трёх оставшихся 2 не хватит по CPU.

Увеличиваем `N`:
```
N = 4:  (4 - 1) × 7 vCPU = 21 vCPU  ≥  17 vCPU  →  ОК
        (4 - 1) × 30 ГБ  = 90 ГБ   ≥  30.25 ГБ  →  ОК
```

**Итог: 4 worker-ноды** — при отказе любой одной ноды оставшиеся три (21 vCPU / 90 ГБ allocable) с запасом покрывают всю нагрузку (17 vCPU / 30.25 ГБ).

---

## Шаг 5. Служебные ресурсы control-plane

Control-plane (`kube-apiserver`, `etcd`, `controller-manager`, `scheduler`) — это **отдельные ноды с другим профилем нагрузки**, чем worker-ноды:
- Им не нужно много ОЗУ под пользовательские поды — их работа связана в первую очередь с обработкой API-запросов и хранением состояния кластера в `etcd`.
- `etcd` критичен к скорости диска (низкая latency записи) и стабильности сети между control-plane нодами — на слабом/медленном диске `etcd` начинает деградировать при росте кластера.
- Для отказоустойчивости самого control-plane нужно **нечётное количество нод** (кворум `etcd`): стандартная практика — **3 ноды** (переживает отказ 1 из 3 без потери кворума).
- Control-plane ноды обычно **тейнтятся** (`NoSchedule`), чтобы пользовательские поды (frontend/backend/БД/кеш) туда не попадали и не конкурировали с системными компонентами за ресурсы.

Размер control-plane ноды для кластера такого масштаба (рабочих подов с приложением - 21): **4 vCPU / 8 ГБ ОЗУ** на ноду — этого достаточно для стабильной работы `etcd` + control-plane компонентов с запасом при умеренном темпе изменений состояния кластера. (Минимальный порог, который указывает сам `kubeadm`, — 2 vCPU/2 ГБ.)

---

## Шаг 6. Итоговый результат

| Тип ноды | Количество | Параметры одной ноды | Allocable (за вычетом резерва) | Назначение |
|---|---|---|---|---|
| **Worker** | **4** | 8 vCPU / 32 ГБ ОЗУ | 7 vCPU / 30 ГБ | Запуск подов приложения (БД, кеш, frontend, backend) |
| **Control-plane** | **3** | 4 vCPU / 8 ГБ ОЗУ | — (не под пользовательские поды, тейнт `NoSchedule`) | `etcd`, `kube-apiserver`, `controller-manager`, `scheduler` |
| **Итого нод в кластере** | **7** | | | |

### Проверка отказоустойчивости итоговой конфигурации
- **Worker-слой:** отказ любой 1 из 4 worker-нод оставляет 21 vCPU / 90 ГБ allocable против требуемых 17 vCPU / 30.25 ГБ — запас есть.
- **Control-plane:** отказ любой 1 из 3 control-plane нод оставляет кворум `etcd` 2 из 3 — кластер продолжает работать.
- **БД и кеш:** при условии anti-affinity (реплики разнесены по разным worker-нодам) отказ 1 worker-ноды убивает максимум 1 реплику БД и 1 реплику кеша — оба компонента остаются в рабочем состоянии (2 из 3 реплик).

## Упаковка в Helm-чарт (п.1 задания)

Рассчитанные `requests` ложатся в `values.yaml` чарта как переопределяемые параметры — это то, что позволяет разворачивать один и тот же чарт в разные окружения (dev/staging/prod) с разными профилями ресурсов и количеством реплик:

```yaml
# Пример фрагмента values.yaml с учётом расчёта выше
database:
  replicaCount: 3
  resources:
    requests:
      cpu: "1"
      memory: "4Gi"
    limits:
      cpu: "1"
      memory: "4Gi"
  # Anti-affinity, чтобы реплики не оказались на одной ноде
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - topologyKey: "kubernetes.io/hostname"

cache:
  replicaCount: 3
  resources:
    requests:
      cpu: "1"
      memory: "4Gi"
    limits:
      cpu: "1"
      memory: "4Gi"
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - topologyKey: "kubernetes.io/hostname"

frontend:
  replicaCount: 5
  resources:
    requests:
      cpu: "200m"
      memory: "50Mi"
    limits:
      cpu: "200m"
      memory: "50Mi"

backend:
  replicaCount: 10
  resources:
    requests:
      cpu: "1"
      memory: "600Mi"
    limits:
      cpu: "1"
      memory: "600Mi"
```

## Что осталось за рамками расчёта

- **Дисковое хранилище (PV) для БД и кеша** в задании не задано в цифрах — реальный размер `PersistentVolume` под данные нужно рассчитывать отдельно, исходя из ожидаемого объёма данных проекта.
- **Сетевые лимиты и IOPS диска** (особенно критично для `etcd` и БД) в расчёте не учтены — при реальном планировании стоит закладывать SSD с гарантированными IOPS под control-plane и БД.
- **Autoscaling** (HPA/VPA/Cluster Autoscaler) не рассматривался — расчёт исходит из фиксированного количества реплик, как задано в условии; в реальном проекте пиковые нагрузки обычно покрывают автоскейлингом, а не постоянным резервом на пике.
